# 관리 화면 예제 (2차)

종합 대시보드와 동일한 디자인 토큰, 사이드바, GNB, 검색과 테마 설정을
사용하는 사용자·주문·상품 관리 예제입니다. 로그인 후 사이드바의 **관리**
그룹이나 전역 메뉴 검색에서 접근합니다.

## 화면과 사용 흐름

| 기능           | 경로                                                | 예제 동작                                                         |
| -------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| 사용자 목록    | `/users`                                            | 이름·이메일·부서 검색, 역할·상태 필터, 정렬, 페이지 이동          |
| 사용자 상세    | `/users/$userId`                                    | 프로필·구매 요약, 기본 정보·주문 내역·활동 로그·권한 설정 탭      |
| 주문 목록      | `/orders`                                           | 주문번호·고객·상품 검색, 상태 필터, 금액·날짜 정렬                |
| 주문 상세      | `/orders/$orderId`                                  | 배송 단계·주문 상품·고객 정보·결제 상세·최근 주문·운송장 저장     |
| 상품 목록      | `/products`                                         | 이미지 카드, 상품명·SKU·브랜드·태그 검색, 판매·재고 필터          |
| 상품 등록      | `/products/new`                                     | 이미지, 상품 정보, 가격·재고·태그·설명 입력                       |
| 상품 상세·수정 | `/products/$productId`, `/products/$productId/edit` | 기본 정보·재고/옵션·판매 통계·리뷰 탭, 이미지·재고·연관 상품 패널 |

목록의 검색·필터·정렬·페이지는 URL search parameter로 관리합니다. 조건을
변경하면 첫 페이지로 돌아가며 상세·편집 화면을 거쳐 목록으로 돌아와도
조건이 유지됩니다. 목록은 페이지당 8건이며 존재하지 않는 페이지 번호는
현재 결과의 마지막 페이지로 보정해 표시합니다. 사용자 상세 탭은 방향키,
Home, End 키로 전환할 수 있습니다. 상품 상세에도 같은 키보드 탭 UI를 사용합니다.

상세 화면은 `design-system-sample`의 `layout-dashboard-user.html`,
`layout-dashboard-product.html`, `layout-dashboard-order.html`의 콘텐츠 구성을
참고합니다. 기존 앱의 공통 디자인 토큰과 반응형 레이아웃을 사용합니다.

## 데이터와 변경 규칙

- MSW fixture: 사용자 24명, 주문 23건, 상품 23개. `/api/users`,
  `/api/orders`, `/api/products`와 각 상세 endpoint를 사용합니다.
- 회원 정보는 `PATCH /api/users/:id/profile`로 이름·닉네임·이메일·연락처·부서·
  회원 등급·주소·메모를 저장합니다. 프로필의 주문 수·구매액은 연결된 주문에서
  계산하며, 주문 당시 고객 정보와 결제 금액은 기존 스냅샷을 유지합니다.
- 역할과 이용 상태 변경은 `PATCH /api/users/:id/access`에 저장하고,
  실제 값이 변경된 경우에만 활동 이력을 추가합니다. 같은 API에서 리뷰·쿠폰·
  이메일·SMS·관리자 패널의 세부 설정도 저장합니다. 실제 알림을 발송하지 않습니다.
- 주문 상태는 **대기 → 배송중 → 완료**, 또는 **대기 → 취소** 흐름입니다.
  완료·취소는 종료 상태입니다. 잘못된 전이는 API에서 409로 거부합니다.
  같은 상태의 재요청에는 이력을 중복 추가하지 않습니다.
- 주문 상태 변경은 `PATCH /api/orders/:id/status`, 메모 추가는
  `POST /api/orders/:id/notes`를 사용합니다. 메모는 1~1,000자입니다.
- 택배사·운송장 번호는 `PATCH /api/orders/:id/shipping`으로 저장합니다.
  주문의 상품 금액 − 할인 − 사용 포인트 + 배송비가 최종 결제 금액입니다.
- 상품은 `POST /api/products`, `PUT /api/products/:id`로 저장합니다.
  SKU는 대문자·숫자·하이픈이며 중복 저장은 409로 거부합니다.
  가격·재고는 0 이상의 정수, 태그는 대소문자 무관 중복 없이 최대 8개입니다.
- 상품 옵션은 색상·사이즈 조합으로 최대 30개이며 대소문자 무관 중복을 거부합니다.
  옵션이 있으면 전체 재고는 옵션별 수량의 합계와 같아야 하며 API도 검증합니다.
  새 상품은 옵션 없이 전체 재고를 입력할 수 있습니다.
- 상품 판매 통계는 2025년 상반기 예제 스냅샷이며 차트는 호버·포커스·터치로
  월별 수량을 표시합니다. 리뷰는 읽기 전용 샘플 데이터입니다.
- 재고 부족은 1~10개, 품절은 0개입니다. 삭제나 재고 자동 차감은 포함하지 않습니다.
- 이미지는 저장소의 기본 SVG 4종 또는 PNG·JPEG·WebP 업로드(최대 2MB)를
  사용합니다. 업로드는 data URL로 미리보기와 mock 저장을 수행합니다.
- 서버 상태는 TanStack Query, 입력은 React Hook Form/Zod, API 응답은
  Zod 검증을 사용합니다. mutation hook은 각 feature의 `queries`에 있으며
  성공 시 관련 목록·상세 query를 갱신합니다.

주문 상태는 종합 대시보드의 최근 주문과 주문 검색에도 반영됩니다. 매출 KPI와
차트는 기존 기준일의 예제 스냅샷으로 유지되며, 상품 가격 수정도 기존 주문의
주문 당시 금액을 변경하지 않습니다.

## 샘플의 범위

변경 데이터는 **현재 페이지의 MSW 메모리**에 저장됩니다. 앱 안에서 이동할
때는 유지되지만 브라우저 새로고침 또는 재시작 시 초기화됩니다. 실제 서버나
이미지 스토리지에는 저장하지 않습니다. 사용자 역할 변경은 관리 데이터 예제이며
현재 로그인 세션의 권한이나 접근 제어를 변경하는 RBAC 구현이 아닙니다.
회원 등급·포인트·세부 권한도 관리 데이터이며 실제 멤버십 정책을 실행하지 않습니다.

## 검증과 컴포넌트 예제

순수 검색·페이지·입력 검증, 실제 fetch/MSW API 통합, 화면 입력·오류 복구
테스트를 제공합니다. `e2e/management.e2e.ts`는 역할 변경, 주문 처리와
대시보드 반영, 상품 이미지 등록·수정, 모바일·데스크톱 흐름을 검증합니다.
Storybook에는 공통 테이블·페이지 이동·로딩/오류·빈 결과·Textarea와 상품
이미지·폼·옵션 재고·판매 통계·리뷰, 상세 탭, 주문 상태 배지 예제가 있습니다. 상품 폼 스토리도 MSW를 사용하며
스토리 로딩 시 관리 fixture를 초기화합니다.

### 관리 폼 Storybook

- `Features/Users/ProfileForm`: 기본·저장·입력 오류·저장 실패·좁은 화면
- `Features/Users/AccessForm`: 기본·초대·이용 중지·저장·저장 실패
- `Features/Orders/StatusForm`: 대기·배송중·완료·취소·저장·저장 실패
- `Features/Orders/NoteForm`: 기본·입력 오류·저장·저장 실패
- `Features/Orders/ShippingForm`: 기본·배송 전·입력 오류·저장·저장 실패

폼 스토리의 `play`는 실제 입력·검증·MSW 저장을 수행합니다. 상태 변경 폼은
저장된 주문 query를 구독하므로 배송 완료 후에는 종료 상태 안내로 바뀝니다.
실패 스토리는 존재하지 않는 샘플 ID를 사용해 404와 입력 보존을 재현합니다.
스토리 ID가 바뀌면 query cache를 새로 만들며, loader에서 관리 데이터를 초기화합니다.

문서는 기본 예제 하나를 iframe으로 표시하고, 저장·검증·오류 play는 개별
스토리에서 실행합니다. 여러 자동 입력이 동시에 실행되어 포커스와 mock 데이터가
섞이지 않게 하기 위한 구성이며, 모든 상태 예제는 사이드바에서 선택할 수 있습니다.

## 저장 중 편집과 저장 기준

배송 정보·회원정보·권한·상품 폼과 관리자 메모는 저장과 관련 query 갱신이 끝날 때까지 입력을 잠급니다. 성공 시 서버 응답의 해당 입력 schema로 폼을 초기화하여 정규화된 값을 저장 기준으로 사용합니다. 실패 시 입력을 보존하고 잠금을 해제하여 재시도할 수 있습니다. 관리자 메모는 성공 후 입력을 비우며, 상품은 성공 응답으로 초기화합니다. 저장 중 후속 초안을 작성할 수 없도록 하여 응답 도착 시 입력이 유실되지 않게 합니다.

## 옵션 목록의 식별자

상품 옵션과 주문 상품의 React key는 색상·사이즈 등의 필드를 배열로 묶어 `JSON.stringify`로 생성합니다. 하이픈 등 구분자가 실제 입력에 포함되어도 서로 다른 옵션이 같은 key를 갖지 않도록 합니다. 상품 schema의 중복 옵션 검증은 기존 대소문자 정규화 기준을 유지합니다.
